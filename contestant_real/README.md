# 真机选手程序（contestant_real）

这是 `contestant_sim/` 的**真机副本**。两边程序逐字节相同，区别只有一个：
`venue.py` 里的场地参数按真实赛场改。

分成独立目录是因为两套坐标必然不同，放在一起迟早改混。想对比改了什么：

```bash
diff -u ../contestant_sim/mission_slim.py mission_slim.py
```

---

## 〇、赛场跟仿真不一样时，按这三条走

仿真场景已经冻结，它是**飞行验证过的那套参考实现**；真实赛场跟它不一致是常态。
先判断差异在哪一层，再决定怎么改，顺序不能颠倒。

1. **能写成 `venue.py` 里的一个值，就到此为止。** 坐标、观察位、朝向、拍照顺序
   （`STATIONS`）、战术参数（前移距离、三个瞄准预算、投弹高度/容差/对准时限、
   弹数）全在 `venue.py`，改它不触发任何闸门，两侧程序仍然同源。

2. **不能，就用新文件名分叉，同名文件永远保持两侧一致。** 真机独有的流程写成
   `mission_real.py` / `rounds_real.py` 这类新文件；`run_real.sh` 的一致性闸门只比
   两侧**同名**的文件，新名字天然豁免，而且翻一眼目录就知道哪个是赛场特供。
   不要去改 `*_slim.py`——一旦允许改同名文件，闸门就从保护退化成噪音。

3. **现场来不及按前两条走，就显式放行并留痕。** 往本目录丢一份 `rounds.py` 会盖过
   SDK 里那份（`/workspace` 排在 PYTHONPATH 最前），立即生效、不用重建镜像；运行器
   带 `--allow-drift` 跑，闸门降级成告警并把漂移清单打进飞行日志。赛后回灌仿真。

绕过闸门本身不危险，危险的是事后没人知道飞的是哪一套——所以第 3 条的重点是留痕。

新流程哪怕场地对不上，**仿真仍然可以当流程试验台**：握手时序、事件顺序、超时、
状态机都能在仿真里跑出来，飞的轨迹对不上没关系，那部分本来就要靠现场试飞。前提是
只跑、不改仿真的 world 和 `src/`。

## 一、必须改的：venue.py

要改的全在本目录的 `venue.py` 一个文件里，别处不用动。现在的值还是**仿真场地**
（`src/contest_mission/config/sample_room_layout.yaml`）：房间 20×25 米、世界原点在
**西南角**、坐标全为正。

| 常量 | 现值 | 含义 |
|---|---|---|
| `ROUTE_A`…`ROUTE_D` | 见文件 | 航线 A/B/C/G/E/F/D 七个点，F 是虚拟点 |
| `POINT_M` / `POINT_N` | `(6.5,16.0)` / `(13.4,16.3)` | 观察位 M（看 2# 楼）/ N（看 1# 楼） |
| `SUPPLY_XY` | `(10.0, 7.8)` | 物资点 |
| `FACADE_YAW_DEG` | `90.0` | 正对楼面的机头朝向。火情贴楼的 -Y 面，所以是正北 |
| `STATIONS` | 3#→2#→1# | 拍照顺序、观察位、机头朝向、这一站查不查火情 |
| `CRUISE_AGL_M` / `OBSERVE_AGL_M` | `2.0` / `2.0` | 巡航 / 观察离地高度 |
| 战术参数一组 | 见文件末段 | 前移距离、三个瞄准预算、投弹高度/容差/时限、弹数 |

⚠️ 本目录用的是**旧楼号**（西南那栋叫 3#），`contestant_sim/venue.py` 里同三栋楼
写作 1#→2#→3#。改的是同三栋实体楼，只有标签不同。

### 改之前必须想清楚的一件事

这里写的是**世界系**坐标，而 `goto()` 吃的是飞机**自己的局部系**——SDK 的
`world_to_local()` 负责换算，依赖**起飞点原点锁定**那条 TF。

所以坐标即便全改对了，**原点标定没做的话整条航线仍会整体偏移**。迁移清单 A4
那项（UWB 原点标定）必须先做。

### 改完怎么验

```bash
python3 tools/check_route.py          # 核航线有没有撞障碍
python3 tools/timeline.py             # 看任务时序
```

⚠ `check_route.py` 里的 `INFLATE_M` 写死是 `0.8`，正好等于真机
`EGO_OBSTACLES_INFLATION` 的值，所以真机用它是对的（仿真那边实际是 0.6，
用它核仿真航线会偏保守）。

## 二、不用改但要知道的

### class_id：真机靠 AprilTag 并行检测

程序找的是 `apriltag:0`（物资）/ `apriltag:1`（高层火情）/ `apriltag:2`（地面火情）。
真机的 YOLO 模型 `best_960` 只认 `StoveCabinet / Campfire / FireBomb`，**认不得
AprilTag**——所以 2026-10-03 在 `yolo_detector_node` 里加了 AprilTag 并行检测
（`cv2.aruco` 的 `APRILTAG_36h11`，跟 YOLO 共用同一帧）。

两套 class_id 现在**同时存在于同一个话题** `vision/detections` 里，靠
`header.frame_id` 区分前视/下视。所以程序不用改。

标靶边长 `TAG_SIZE_M = 0.5`，真机也是 0.5 米，SDK 里不用改。

### 相机内参：自动适配，不用管

`aim_at` 读 `camera_info`：仿真拿 Gazebo 相机的值，真机拿实测标定值（2026-10-15 起
两机四路同型号、共用一组 fx=735.455 / cx=616.22 / cy=376.47），同一份 SDK 两边都对。

### 综合任务的火情：人工布置

`mission_slim` 在仿真里靠 `referee.py` 增删 Gazebo 模型让火情随机出现。真机没有
这个手段，火情按赛前约定**人工布置**。

## 三、怎么跑

```bash
./vision_real.sh up           # 起机载视觉（两机×两路），等 10 秒
./vision_real.sh status       # 体检：应有 2 个节点/机、10 条话题
./run_real.sh formation_slim  # 跑程序（前置闸门自动把关）
./stop_real.sh                # 急停
```

### ⚠ `stop_real.sh` 不会让飞机降落

选手程序发的是任务级指令，掐掉之后机载 `ego_planner` 会把最后一条轨迹执行完、
然后**悬停在那里**。真正的应急手段是**遥控器接管**——那是安全保障手段，飞行时
必须在手。`--land` 是显式可选项，就地降落、落点不保证是起降垫。

### `run_real.sh` 的五道闸门

| 闸门 | 不过会怎样 |
|---|---|
| 两机 ping 可达 | 中止 |
| `/status` 的 `flight_up` + `vision_up` | 中止 |
| 命名空间对应（.101→NX01、.102→NX02） | 中止——配反了话题会全错位且不报错 |
| 视觉就绪（两条 `vision/detections` 有发布者） | 中止——检测节点不随栈自启 |
| 声光域号必须是 20 | 警告 |

另外起飞前还会调 `scripts/check_env.sh real` 查仿真残留。
