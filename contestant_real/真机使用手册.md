适用：双机真飞行（NX01 侦察机 / NX02 任务机 + 地面站）。
仿真请看 `contestant_sim/README.md`，两边**程序代码相同、只有 `venue.py` 的坐标不同**。

|---|---|---|

## 1. 机载容器是怎么起来的

这是最容易误解的一环，分三层说。

### 1.1 开机只自启一个东西：`control_server`

两台飞机上唯一 enable 的业务 unit：

```
/etc/systemd/system/uav-control-server.service
  ExecStart=/usr/bin/python3 /home/nvidia/ai_uav/docker_sim/scripts/control_server.py
  Restart=always   RestartSec=3
  After/Wants=docker.service network-online.target
```

它**不是**飞行栈，它是飞行栈的遥控开关。开机后它就在那儿听着，但**容器一个都没起**。

### 1.2 容器是被 HTTP 请求起来的，不是开机起的

两个容器的 restart policy 都是 `no`：

```
docker_sim-flight-stack-hw-1   restart=no
docker_sim-vision-stack-1      restart=no
```

所以飞机开机 ≠ 飞行栈就绪。容器由 `control_server` 收到请求后，代它执行
`docker compose -f docker-compose.hw.yml up -d <service>`：

| 端点 | 请求体 | 作用 |
|---|---|---|
| `POST /stack` | `{"stack":"flight"\|"vision", "action":"up"\|"down"\|"restart", "confirm":true}` | 启停容器 |
| `POST /stack/mode` | `{"localization","slam","planner","controller"}` 四项可省 | **只写 `.env`，不碰容器**；返回 `restart_required` |
| `POST /vision/mode` | `{"cam":"cam0"\|"cam1"\|"all", "mode":"yolo"\|"apriltag"\|"raw"\|"stop"}` | 切某一路相机的检测模式 |
| `POST /params` | `{"changes":{"KEY":"值"}, "remove":[...], "restart":false}` | 改 `.env`；写前备份、校验失败自动回滚 |
| `POST /rename` | `{"namespace":"NX0x"}` | 改 `.namespace` 并重启两个容器 |
| `GET /status` `/params` `/api` | — | 读状态、读参数、读接口契约 |

`confirm:true` 是 **flight 的 `down`/`restart`** 必须带的。写操作都记审计日志
（"到底是谁把飞控停了"）。

`GET /api` 是**运行时拿到的权威契约**，合法取值由 `STACK_CHOICES`/`HW_FORBIDDEN`
常量生成，不会和实现漂移——以它为准，不要以本手册为准。

可切的 stack（`POST /stack/mode`）：

```
LOCALIZATION_SOURCE  gt* / uwb_slam / uwb_imu / single_slam_only / single_uwb_imu / single_uwb_slam
SLAM_BACKEND         dlio / point_lio / fast_lio
PLANNER              mighty / ego_planner
CONTROLLER           px4ctrl / so3ctrl / pt4ctrl
```

`*` 真机 `HW_FORBIDDEN` 拦掉 `gt`：真机没有 Gazebo 真值，`gt_odom_bridge_node`
永远收不到数据，entrypoint 会 `exit 1`。

实际操作有两条路：
- **地面站界面点按钮** —— 正常用法。地面站先收 UDP 心跳发现飞机，再调上面这些端点。
- **手敲 curl** —— 调试用，例子见 §4.2、§6。

### 1.3 NAMESPACE 从文件来，不从环境变量来

`~/ai_uav/docker_sim/.namespace` 一行纯文本（.101 是 `NX01`，.102 是 `NX02`）。
`control_server` 读这个文件，用 `extra_env={"NAMESPACE": ns}` 注进 compose。

这么设计的原因：开机时不需要人在场 `export`，地面站故障/断网时飞机也照样用本机
命名空间工作。`POST /rename` 可以改它。

> ⚠️ `.namespace` 和 `compose` 的 `NAMESPACE` 默认值要一致。两机 compose 默认值
> 已分别改成本机实际值，作为兜底。

### 1.4 视觉节点不随飞行栈起，而且不持久化

vision-stack 容器起来之后，**检测节点并没有在跑**。要再 `POST /vision/mode` 把每一路
相机的模式打开。容器一重启，上次的模式**不恢复**。

四种模式，**同一路相机上互斥**：

| mode | 作用 |
|---|---|
| `yolo` | 目标检测（真机上 AprilTag 与它**并行**跑，`apriltag_every_n=3`） |
| `apriltag` | 只跑 AprilTag |
| `raw` | 纯视频直通，不推理，只把原始帧推给 MJPEG |
| `stop` | 停掉这一路 |

飞行用 `yolo`（两路都要）。`mjpeg_draw_detections:false` 可以让地面站拉到不叠检测框的画面。

漏掉一路的后果是静默的：话题根本不存在（不是发空数组），选手程序里
`wait_for_detection()` 会一直等到超时。所以有 `vision_real.sh` 这个脚本——
两机 × 两路共四条 curl，手敲太容易漏。

### 1.5 两个关于容器的坑

- **`--force-recreate` 会毁掉容器内 colcon 的编译产物。** 日常起停用 `up -d`，
  不要随手加 `--force-recreate`。
- **改 `.py` 不用重建镜像。** `vision_stack` 是 `--symlink-install` + egg-link 装的，
  改完**重启节点**就生效。改 C++ / 加依赖才需要 build。

## 2. 数据走几个通道

飞行时**同时存在 9 条**。前 4 条跨机，后 5 条机内或旁路。

### 跨机（走 WiFi，AP 是 TL-XAP3001GP，5G ch149/80MHz）

**① ROS 2 / CycloneDDS —— domain 20，网卡 `wlP1p1s0`**

承载全部任务数据：里程计、位置指令、检测结果、编队状态、声光事件、
`set_origin_from_uwb` 服务、参数读写。三方（NX01 / NX02 / 地面站）共用一个域。

AP 下多播不可靠，所以用**静态单播 Peers**。真正生效的配置不是 compose 里那行，
而是 entrypoint 在容器内生成的 `/tmp/docker_sim_cyclonedds.xml`：

```xml
<NetworkInterface name="wlP1p1s0" priority="default" multicast="true"/>
<AllowMulticast>true</AllowMulticast>
<Discovery><Peers>
  <Peer address="192.168.2.103"/>   <!-- 地面站 -->
  <Peer address="192.168.2.102"/>   <!-- 友机，NX02 上这里是 .101 -->
</Peers></Discovery>
```

> ⚠️ `docker-compose.hw.yml` 里 flight-stack-hw 那行 `CYCLONEDDS_URI=...enP8p1s0...`
> 是**被 entrypoint 覆盖的死值**，别照它判断。而且
> `docker exec <容器> env` 看到的也是 compose 注入的那份，不是生效的那份。
> 要看真值，读 `/tmp/docker_sim_cyclonedds.xml`，或者
> `tr '\0' '\n' < /proc/<节点PID>/environ`。
>
> 仿真是 **domain 21**，真机是 **20**，靠这个隔离。`check_env.sh` 会在起飞前验。

**② control_server HTTP —— TCP 8890**

地面站 → 各机的**带外管控**：起停容器、切视觉模式、读状态。不经 ROS，
所以飞行栈挂了、DDS 不通了，这条路还在，能用来救场。局域网内无鉴权
（写操作要 `confirm`）。

**③ 发现心跳 —— UDP 8891 广播**

各机 → 地面站，2 秒一次 JSON：`{"namespace","ip","control_port","stack",...}`。
每轮重新枚举网卡、逐网段用该网段自己的源地址和广播地址发（换 AP / DHCP 续租
/ 开机网络未就绪都会让"启动时算一次"算错）。心跳里的 `ip` 是**发出这份心跳那块
网卡自己的地址**。

**④ MJPEG 图像预览 —— TCP 8080 / 8081**

`yolo_detector_node` 自己起的 HTTP 服务（容器 `network_mode: host`，端口直接暴露在
飞机 IP 上）。对应关系是固定的：

```
cam0 = front = sensor_id 0 = 8080   frame_id {ns}_camera_front_optical_frame
cam1 = down  = sensor_id 1 = 8081   frame_id {ns}_camera_down_optical_frame
```

```
http://192.168.2.101:8080   NX01 前视
http://192.168.2.101:8081   NX01 下视
http://192.168.2.102:8080   NX02 前视
http://192.168.2.102:8081   NX02 下视
```

> 本机有代理会截内网请求，拉这些流要绕代理（`no_proxy` / `-x ""`）。
> **502 不等于服务没起。**

### 机内（不出飞机）

**⑤ MAVLink 串口** —— `/dev/ttyTHS1` @ 921600，mavros ↔ 飞控。

**⑥ 激光雷达以太网** —— `enP8p1s0`，192.168.1.5/24，雷达 → 里程计。
真机 `LIDAR_TILT_DEG=0`（水平安装，代码注释里"前倾 25°"已过时）。

**⑦ UWB 串口 ×2** —— `/dev/uwb_a` `/dev/uwb_b`（CH341 udev 别名）@ 921600，
用于原点标定（§3）。

### 旁路

**⑧ 遥控器 → 飞控**（2.4G 直连，不过 Jetson）
**这是唯一的安全保障手段。** `PX4CTRL_NO_RC=false`，飞行时遥控器必须在手。
掐选手程序不会让飞机降落（见 §5）。

**⑨ 声光设备 —— 地面站的 CH340 串口**
地面站上 `contest_sdk.sound_light_server` 常驻，订阅 domain 20 的事件话题，
驱动串口上的声光设备。注意 **`brltty` 会抢 CH340**，被抢了要先停它。

## 3. 原点标定（每次通电后必做一次）

机载 `origin_setter_node` 提供一个 ROS Trigger 服务。调它的那一刻，节点采样 UWB，
把 world→odom 的**平移**锁死（旋转 θ* 是另算的，在线用滑窗最小二乘
`θ*=atan2(S,C)` 估，不在这一步锁）。

```bash
# 在飞机上执行（NX02 把 NX01 换成 NX02）
ssh nvidia@192.168.2.101 'docker exec docker_sim-flight-stack-hw-1 bash -lc \
  "source /opt/ros/humble/setup.bash && export ROS_DOMAIN_ID=20 && \
   ros2 service call /NX01/set_origin_from_uwb std_srvs/srv/Trigger"'
```

判据（节点参数）：`sample_window_sec=2.0`、`min_samples=5`、`max_std_dev_m=0.15`。
结果存 `/tmp/uwb_origin_{ns}.json`，同时发 `origin_locked`(Bool) 和静态 TF
`world → {ns}/map`。

**⚠️ 必须等里程计收敛了再锁。** 没收敛就锁过一次，world→odom 永久带偏 0.47/0.67 米，
整场飞行都歪。现在加了"静止 + 雷达一致性"判据，但**人也要确认**：
飞机放稳别动、雷达出点云、`/{ns}/odom` 不漂，再调。

锁成功的标志：服务返回 `success=True`，且 `ros2 topic echo /{ns}/origin_locked`
是 `true`。

## 3.5 双机基础动作测试（`basic_test.py`）

真机第一次通电、换场地、换参数之后，**先跑这个再跑任务程序**：

```bash
./run_real.sh basic_test
```

动作：起飞 1.2 m → 悬停 5 s → 沿机头前飞 1.5 m（**走规划器**）→ 悬停 5 s → **回起降垫降落**。
两机跑同一段动作但**各自独立、无编队无握手**，所以一架有问题不会连带另一架。

只验四件最基础的事，不碰航线/视觉/避障：能否解锁起飞到指定高度、悬停稳不稳、
能否按机头方向走一个确定的小位移、能否正常降落上锁。

看什么：
  · 监视里两条轨迹应是"原地 → 前移1.5米 → 退回原地"，悬停段是个点而不是一团
  · **日志里 `当前机头 +xx.x°` 要和飞机实际摆放的朝向对得上** —— 对不上就别放手
  · 声光应响四次（两机起飞各一次、两机降落各一次）—— 顺带验了声光链路
  · **日志末尾会报落点是否在起降垫容差内，这一项是硬判据**

> 降落走 `return_home()`：飞回自己起飞点 → 按落点坐标核对 → 核对通过才播
> 降落声光。1 米回程短于 `RETURN_HOME_FAR_M`(2.0)，直接进精修段。它内部用
> `land_or_confirm()`，兜住"贴地了但 PX4 不报 Landing detected"那个老坑。
>
> 前飞走 `goto()`（→ `waypoint_queue` → `ego_planner_bridge` → 规划器，有避障），
> 定高用局部系 z 且等于该段 goto 的 z。
>
> ⚠️ **"前"是机身此刻的实际朝向**，不是地图上某个固定方向 —— `takeoff()` 保持
> 起飞前的真实 yaw，所以**两机摆放朝向不同就会各自朝不同方向飞**。程序会把
> 实测航向角打进日志，起飞后先核这个数。
>
> ⚠️ 回程仍是直线：1.5 m 短于 `RETURN_HOME_FAR_M`(2.0)，`return_home` 不走
> 远距离那条规划器分支、直接进精修段。所以正前方那 1.5 米还是要空出来。

## 4. 单机测试程序（`单机测试/`）

先用单机测试把五项能力逐个过一遍，再上双机任务。

| 测试 | 内容 | 默认机号 |
|---|---|---|
| `t1` | 物资抓取 | **NX02**（要夹爪） |
| `t2` | 地面火情对准 | NX01 |
| `t3` | 高层火情瞄准（`--n` 用 N 点看 1# 楼） | NX01 |
| `t4` | 避障 | NX01 |
| `t5` | 仿地 | NX01 |

### 4.1 步骤

```bash
cd ~/ai_uav/docker_sim/contestant_real

# ① 飞机通电，等 control_server 上线（开机自启，约 10 秒）
curl -s --noproxy '*' http://192.168.2.101:8890/status | head -5

# ② 起机载栈（地面站界面点按钮，或 curl）
curl -s --noproxy '*' -X POST http://192.168.2.101:8890/stack \
     -d '{"stack":"flight","action":"up","confirm":true}'
curl -s --noproxy '*' -X POST http://192.168.2.101:8890/stack \
     -d '{"stack":"vision","action":"up","confirm":true}'

# ③ 起视觉检测（容器起来了节点还没跑，必做）
./vision_real.sh up
./vision_real.sh status        # 四路都该是 yolo

# ④ 原点标定（见 §3），确认 origin_locked=true

# ⑤ 跑测试（遥控器在手！）
./run_test.sh t1                      # 抓取，默认 NX02
./run_test.sh t3 --n                  # 高层火情，N 点
./run_test.sh t4 --nx02               # 避障，指定 NX02
./run_test.sh t5 --keep               # 仿地，留容器看日志
./run_test.sh                         # 不给参数就列出可选项
```

参数：`./run_test.sh t1 [--nx01|--nx02] [--keep] [--timeout 秒] [程序自己的参数...]`
不认识的参数原样转给测试程序。

### 4.2 `run_test.sh` 做了什么

1. **清残余**：`purge_stale()` 先 `docker rm -f` 掉同名的旧容器（见 §7）
2. **闸门**：`check_env.sh real` —— 查有没有仿真容器在跑、声光域号、地面站域号
3. **轮询就绪**：两机 ROS 节点可见 + 检测话题有发布者（原来是 `sleep 25`，现在轮询，约 2 秒）
4. **起监视窗口**（单机也开，这是硬规矩）
5. 起选手容器跑程序，`trap cleanup EXIT` 兜底收尾

## 5. 双机任务程序

```bash
cd ~/ai_uav/docker_sim/contestant_real

./run_real.sh formation_lite      # 编队飞行
./run_real.sh groundfire_lite     # 地面火情
./run_real.sh highrise_lite       # 高层火情
./run_real.sh mission_lite        # 三轮连贯
./run_real.sh                     # 不给就跑 formation_lite
./run_real.sh highrise_lite --keep
```

参数就是本目录里的程序文件名，`.py` 可省，可 Tab 补全。

### 5.0 run_real.sh 会替你起什么（2026-10-03 起）

| 栈 | 谁起 |
|---|---|
| 声光栈 | **run_real.sh 必起**，而且保证在真机域 20——域不对会自动停掉重起 |
| 网页栈 | **run_real.sh 必起**（`gcs-gcs-1` + `gcs-backend-1`，走 `scripts/up_gcs.sh`） |
| 选手栈 | run_real.sh 起（`real_leader` / `real_follower`） |
| 监控栈 | run_real.sh 起（`real_monitor`）。起不来**只警告、不中止**——但那一轮就没有编队间距记录和报告图 |
| **机载栈** | **仍然不代起**——只探测，不过就中止并打出 `POST /stack` 的 curl |
| 机载检测节点 | 仍要你 `./vision_real.sh up` |

`run_test.sh` 要求相同。仿真侧 `run.sh` 必起仿真栈/选手栈/声光栈(域 21)/监控栈，
网页栈不管（它只用于观察）。

### 5.1 完整流程

```
两机通电 → control_server 上线
   ↓
起 flight-stack-hw + vision-stack（两机，地面站界面或 curl）← 只有这步要人工
   ↓
./vision_real.sh up && ./vision_real.sh status      ← 四路确认
   ↓
两机各调一次 set_origin_from_uwb，确认 origin_locked   ← §3
   ↓
遥控器上电、解锁确认在手
   ↓
./run_real.sh <程序>        ← 声光栈/网页栈/选手栈/监控栈都它起，自带闸门
   ↓
飞行中盯监视窗口
   ↓
正常结束：程序自己降落
异常：遥控器接管（首选） / ./stop_real.sh
```

### 5.2 `run_real.sh` 和仿真 `run.sh` 的区别

- **不起仿真容器**，也不替你启动机载栈，收尾时也不拆机载栈——机载栈归
  `control_server` 管（生命周期比一次飞行长，重起还要重锁原点）。本脚本只**探测**，
  但探测不过时会把该敲的命令原样打出来：

  ```
  !! 192.168.2.101 的 flight-stack 没起（/status: flight_up=False）
     起它：地面站界面点按钮，或
       curl -s --noproxy '*' -X POST -H 'Content-Type: application/json' \
            -d '{"stack":"flight","action":"up","confirm":true}' \
            http://192.168.2.101:8890/stack
  ```

  `control_server` 本身没响应时给的是 `systemctl` 命令（那是服务挂了，不是容器没起）；
  检测节点没起时给的是 `/vision/mode` 的 curl 和 `./vision_real.sh up` 的捷径。
  三种失败各给各的补救命令，`run_test.sh` 同。
- **就绪判据不同**：仿真等 Gazebo 日志的 `"Ready for takeoff"`；真机等两机
  ROS 节点可见 + 检测话题有发布者。

### 5.3 真机没有裁判

`mission_lite` 在仿真里由 `referee.py` 出题（增删火情）。真机上**火情要人工布置**，
程序只管飞和识别。

### 5.4 停止

```bash
./stop_real.sh            # 掐地面站的选手程序 + 监视，不动机载栈
./stop_real.sh --check    # 只看会动什么
./stop_real.sh --land     # 额外给两机发降落指令

./stop_all.sh             # 关掉地面电脑上**一切**真机相关栈（见下）
./stop_all.sh --check     # 只看会动什么
./stop_all.sh --keep-gcs  # 保留网页栈
```

`stop_all.sh` 比 `stop_real.sh` 多关四样（选手容器和监视仍交给 `stop_real.sh`）：

| | 说明 |
|---|---|
| `real_test` / `real_test_monitor` | `run_test.sh` 起的单机测试容器 |
| 声光栈 | **只在它处于真机域 20 时才关**；挂在 21 域的是仿真那套在用，不动 |
| 网页栈 | `run_real.sh` 必起它，所以这里也负责关（`--keep-gcs` 可留） |
| `contestant-sdk-shell` | 调试容器，同样按域判断 |

> ⚠️ **机载容器一个都不碰**，飞机也不会因为这两个脚本降落 —— 应急靠遥控器。

> ⚠️ **掐掉选手程序不会让飞机降落。** 选手程序发的是任务级指令，掐掉之后机载
> `ego_planner` 会把手上最后一条轨迹执行完，然后**悬停在那里**。
> 真正的应急手段是**遥控器接管**。这个脚本的用处是"止住新指令"。
>
> `--land` 发 `TakeoffLand{LAND}`，**就地**降落——落点不一定是起降垫，
> 用之前先确认正下方没人没障碍。

## 6. 要改的东西：`venue.py`

真机和仿真**程序代码完全一样**，差异全集中在 `venue.py`。换场地只改这一个文件：

| 项 | 说明 |
|---|---|
| `ROUTE_A` … `ROUTE_D` | 四条航线的航点 |
| `POINT_M` / `POINT_N` | 两个观察点 |
| `SUPPLY_XY` | 物资点 |
| `SUPPLY_TAG` / `HIGH_FIRE` / `GROUND_FIRE` | 三类目标的标识/位置 |
| `FACADE_YAW_DEG` | 楼立面朝向 |
| `STATIONS` | 起降点 |
| `CRUISE_AGL_M` / `OBSERVE_AGL_M` | 巡航/观察高度 |

> 场地布置基本一致，但**坐标一定要实测后重填**。
> 本目录只有四个 `*_lite.py`，没有 `normal/` 版——那套是硬编码坐标的旧写法，已删。

### 6.1 关键飞行参数在 `.env`

两机 `~/ai_uav/docker_sim/.env`（89 项）。常调的：

```

A_MAX / OMEGA_MAX
GOAL_RADIUS / GOAL_SEEN_RADIUS
EGO_YAW_DOT_MAX

HW_NETWORK_INTERFACE=wlP1p1s0
FORMATION_*                   # 15 项编队参数
```

改完要重启 flight-stack-hw 才生效。

### 6.2 几条调参上的禁忌

- **ego_planner 本身不要改。** 规划器是考核的一部分。
- **`0.8` 膨胀半径是有意设的，别动。**
- **避障不能绕。** A→B 航段 (3,8) 那根柱子是考核点，不能直飞也不能加中间点；
  西侧窄缝有擦墙风险。直飞只在解散后用（限速拐点 1.0，用完恢复 0.3）。
- **定高必须用局部系 z**，且等于该段 `goto` 的 z，否则永远判不到点。
  远距离转场都该包 `fixed_altitude`。

## 7. 两次运行之间怎么保证没残余

### 7.1 脚本自己做的

`run_real.sh` / `run_test.sh` 都有两道（跟仿真 `run.sh` 一致）：

- **开跑前** `purge_stale()`：`docker rm -f` 掉同名旧容器
- **退出时** `trap cleanup EXIT`：不管正常结束、Ctrl-C 还是出错，都收尾

### 7.2 闸门查交叉污染

`scripts/check_env.sh sim|real` 在两个运行器里都接了，查三件事：

1. **对侧容器在不在跑** —— 跑真机时有仿真容器 = 拦
2. **声光程序的域号** —— 挂在 21 上就收不到真机事件
3. **地面站自己的域号**

### 7.3 机载侧要人工确认的

机载栈不归脚本管，所以这几样要自己看：

```bash
# 视觉模式（容器重启后不恢复）
./vision_real.sh status

# 原点有没有锁、锁的是不是这次的
ssh nvidia@192.168.2.101 'cat /tmp/uwb_origin_NX01.json'

# 上一次飞行的节点有没有残着
ssh nvidia@192.168.2.101 'docker exec docker_sim-flight-stack-hw-1 bash -lc \
  "source /opt/ros/humble/setup.bash && export ROS_DOMAIN_ID=20 && ros2 node list"'
```

**换场次 / 换程序时，最干净的做法是重起机载两个容器 + 重锁原点。**

## 8. 排障速查

| 现象 | 先查 |
|---|---|
| 检测话题不存在，`wait_for_detection` 超时 | `./vision_real.sh status`，大概率漏了一路 |
| 飞机位置整体偏半米左右 | 原点锁早了，重锁（§3） |
| 看不到友机话题 | `/tmp/docker_sim_cyclonedds.xml` 里 Peer 对不对；AP 是不是跳到 2.4G |
| 拉 8080/8081 返回 502 | 本机代理截了内网，加 `--noproxy '*'`；**502 ≠ 服务没起** |
| 声光不响 | `brltty` 抢了 CH340；或声光程序域号是 21 |
| 改了 `.py` 不生效 | 重启节点（symlink-install 不用重建镜像） |
| 容器起来但节点是僵尸 | 看容器日志，`control_server` 报"已启动"只代表 compose 返回成功 |
| 判断真机行为 | **一律读真机上的文件。** 仿真和真机的同名文件内容不同 |
| 查 CPU 占用 | 用 `/proc/<pid>/stat` 差分；`ps pcpu` 是**生命周期平均值**，看不出瞬时 |
